### Issues: #17 and #419 – System Admin scope and Organization creation flow

This plan aligns the platform with the principle that System Admins have infrastructure-level privileges only and no inherent access to tenant data (organizations, events, incidents) unless explicitly granted relevant roles. It also defines the desired organization creation flow initiated by a System Admin that generates an invitation for the first Organization Admin rather than implicitly assigning org-level access to the System Admin.

References
- Issue #17: Restrict System Admin rights to infra-level only (no data access)
- Issue #419: Review org creation process and flow

Current state (findings)
- Backend RBAC
  - `requireRole` allows routes to include `system_admin` as an allowed role, granting access when present.
  - Many event and some org data endpoints explicitly include `system_admin` in `requireRole([...])`.
  - `requireSystemAdmin` is correctly used for system-level operations.
  - Unified RBAC service exists and supports role checks per scope (`system`, `organization`, `event`).
- Organization creation
  - `OrganizationService.createOrganization` currently auto-grants `org_admin` to `createdById` (the creator). If a System Admin creates an org, they become an Org Admin, which conflicts with Issue #17 intent.
  - Organization invite links are supported via `OrganizationService.createInviteLink`, but not currently auto-generated during org creation.
- Frontend
  - The admin UI reveals navigation based on `isSystemAdmin`, sometimes surfacing event/org data paths.
  - `pages/admin/organizations/new.tsx` states “The organization will be created with you as the initial admin,” which contradicts the desired flow.
- Docs
  - Several API docs list System Admin as allowed for event-level operations; these need revision to reflect no implicit data access.

Outcome goals
- System Admins can manage system settings, create orgs, manage global integrations, but cannot access org/event/incident data unless explicitly granted an org or event role.
- When a System Admin creates an org, the System Admin is NOT added as an org member. Instead, an `org_admin` invitation is generated and returned/displayed so the System Admin can share it.
- Frontend and API reflect the new model consistently. Documentation updated.

Plan of record
1) RBAC enforcement changes (API)
   - Remove `system_admin` from allowed roles on event- and org-scoped data endpoints that are not system-level operations.
   - Ensure these endpoints require appropriate `event_admin`, `responder`, `reporter`, or `org_admin`/`org_viewer` roles as applicable.
   - For any admin routes that operate on event data (e.g., creating event invites in admin routes), switch from `requireSystemAdmin()` to the correct scoped role check (e.g., `requireRole(['event_admin'])` for that event).
   - Keep `requireSystemAdmin()` strictly for system-level endpoints (global settings, provider configs, listing organizations globally, etc.).

2) Organization creation flow
   - Update `OrganizationService.createOrganization` to stop auto-granting `org_admin` to the creator when the creator is a System Admin.
   - Automatically generate a single-use `org_admin` invitation link upon org creation and return it with the response payload when creator is System Admin.
   - If the creator already has an org-level role (non-System scope), preserve existing behavior to avoid breaking self-service org creation for org admins (if applicable in future flows).

3) Frontend updates
   - `admin/organizations/new`: after successful creation, display the invitation link and instructions instead of implying the creator becomes the org admin.
   - Sidebar and other nav: ensure event/org data sections are not shown merely due to `isSystemAdmin`. Only show those sections if the user has the relevant scoped role.
   - Ensure any event-level actions that previously relied on System Admin presence are gated by event/org roles only.

4) Documentation updates
   - Update roles and permissions docs to explicitly state System Admins have no implicit access to tenant data.
   - Update Organizations API docs to describe the new creation flow and returned invite link.
   - Update any API references that list System Admin as allowed for event/org data endpoints.

5) Tests
   - Adjust existing tests that assume System Admin can access event data.
   - Add integration tests:
     - System Admin cannot read event incidents unless granted event role.
     - System Admin cannot create event invites via admin route unless they are `event_admin` for that event.
     - POST `/api/organizations` as System Admin returns an `org_admin` invite link and does not add the creator to the org membership.
     - Accessing the new org as the creator (System Admin without org role) is forbidden until the invite is redeemed by an org admin.
   - Add frontend tests for the updated create-organization page showing invite link and not assuming membership.

6) Migration and operational considerations
   - Identify existing organizations where System Admin users were auto-assigned `org_admin` solely due to org creation. Provide a one-time script to list these memberships for review and optional removal (do not auto-remove in production without explicit approval).
   - Communicate the change as a security hardening update and include docs on how System Admins can collaborate by inviting an initial Org Admin.

Scope of edits (indicative, not exhaustive)
- Backend
  - `backend/src/routes/event/**/*.ts` and other event data routes: remove `system_admin` from `requireRole([...])` arrays.
  - `backend/src/routes/admin.routes.ts`: for event invite endpoints and any event-scoped admin actions, replace `requireSystemAdmin()` with scoped role checks.
  - `backend/src/services/organization.service.ts`: modify `createOrganization` to not auto-grant org admin to System Admin creators; create and return an `org_admin` invite.
  - `backend/src/controllers/organization.controller.ts`: include invite in response payload when creator is System Admin.
  - Keep `requireSystemAdmin()` for purely system-level endpoints.
- Frontend
  - `frontend/components/app-sidebar.tsx`: stop showing event/org data nav for `isSystemAdmin` alone.
  - `frontend/pages/admin/organizations/new.tsx`: show invite after creation; update copy; remove claim that creator becomes org admin.
  - Review other admin pages for implicit System Admin-based data access surfaces.
- Docs (website)
  - `website/docs/security/access-control/*`, `website/docs/developer-docs/api/*` reflecting the above.

Risks and mitigations
- Risk: Breaking workflows that relied on System Admins reading data for troubleshooting. Mitigate by documenting “temporary role grant” practices and providing tooling to grant/revoke scoped roles quickly.
- Risk: Existing tests may assume System Admin data access. Mitigate by updating tests and adding new ones to assert correct behavior.
- Risk: Orgs previously created by System Admins now have lingering org_admin memberships. Mitigate with a review script and manual confirmation before removal.

Acceptance criteria
- System Admin cannot access event/org/incident data without appropriate scoped roles.
- Creating an organization as a System Admin does not add the System Admin as an org member; an `org_admin` invite is generated and returned/displayed.
- UI no longer surfaces tenant data solely due to System Admin role.
- Documentation is updated and tests pass.
